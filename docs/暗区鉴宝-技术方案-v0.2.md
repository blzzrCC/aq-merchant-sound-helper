## 1. 项目定位

### 1.1 问题陈述（已精确化）

《暗区突围：无限》自 S7 赛季「理想国」起加入局内「战地行商」机制。玩家可在行商处购买**神秘物资 / 神秘箱子**，其内容物在交易完成前**不显示图片**，官方描述为："低价神秘货物收益整体更为稳定；高价神秘货物收益两极分化明显，既存在暴富的机会，也有不小的亏损风险。"

玩家的唯一线索是：**拖动物品时游戏播放的拾取音效**。本工具采集该音效并反推物品身份，为购买决策提供参考。

### 1.2 产品目标

在玩家完成一次拖拽动作后 **1 秒内**，于独立窗口输出：

1. 该音效对应的**候选物品集合**（可能唯一，也可能多件共用）；
2. 每个候选的**市场参考价**与**价格区间**；
3. 基于价格的**建议标记**（值得买 / 需谨慎 / 不建议）；
4. 支持玩家按**占用格数 / 价格档位**手动筛选，收敛候选集（见 §5.5）。

### 1.3 明确不做的事

| 不做 | 原因 |
|---|---|
| 不读写游戏内存 | 触发 ACE 反作弊，封号风险极高 |
| 不注入 DLL / 不 Hook 游戏进程 | 同上 |
| 不覆盖游戏画面 | Overlay 是反作弊重点监控形态 |
| 不自动操作（自动购买 / 自动拖拽 / 自动跑刀） | 官方「负面清单」明令禁止的脚本行为 |
| 不修改任何客户端文件 | 官方处罚规则直接列举的违规项 |
| **不采集游戏画面（截图 / OCR / 模板匹配）** | 避免任何形式的画面采集行为 |

## 2. 关键约束

约束来自实机反馈与外部权威依据，是整套设计的出发点。

### C1 — 音效与物品不是一对一映射

**实机确认：部分物品有专属音效，另一些物品共用同一个音效。**

参考站内置 FAQ 给出了同样的结论，原文："不一定。游戏中多件藏品可能共用同一种拾取音效。"

设计后果：

1. **识别粒度是「音效事件」而非「物品」。** 系统输出单位定义为 **音效类（Sound Class）**。
2. **核心数据结构是「音效类 → 候选物品列表」的多对多映射。**
3. **输出必须显式表达不确定性：**

   | 候选数 | 输出形态 | 产品价值 |
   |---|---|---|
   | 1 | `精确命中` — 直接给物品名与价格 | 高 |
   | 2 ~ 5 | `候选集` — 按价格排序 | 中 |
   | > 5 | `类别提示` — 只给类别与价格区间 | 低 |

4. **引入「共音分组率」作为核心业务指标**（详见 §7.2）。

### C2 — 显示载体不覆盖游戏

**已确认：无副屏可用，采用「游戏内场景下弹出置顶窗口」方案。**

由此产生两条工程约束：

- 若游戏运行在**独占全屏（Exclusive Fullscreen）**模式，任何置顶窗口都无法显示在其上方 —— 这是 Windows 显示机制决定的，不是权限问题。**硬前提：游戏必须运行在无边框窗口化（Borderless Windowed）模式。**
- 工具不读取游戏画面，因此**不需要也不会实现 UI 状态识别**（详见 §5.2 末段）。

#### C2.1 合规判断：外部置顶窗口 ≠ 游戏内 Overlay

这两个形态经常被混为一谈，但风险等级差距很大，必须分清：

| 形态 | 是否接触游戏进程 | 官方态度 |
|---|---|---|
| 内存读写 / DMA 设备 | 是 | 明确封禁，官方通报中大量案例 |
| 注入 DLL / Hook 渲染管线 | 是 | 明确封禁 |
| 游戏内 Overlay（透明覆盖） | 是 | 重点监控；官方资料提示覆盖层可能触发误报 |
| 自动化脚本（代操作） | 否，但代替玩家操作 | 官方「负面清单」明令禁止 |
| **外部置顶窗口 + 音频监听（本方案）** | **否** | **未见公开封禁案例** |
| 手机看攻略 / 第二屏查价表 | 否 | 不违规 |

**本方案与官方打击目标之间存在三条硬区隔：**

1. **不注入、不 Hook、不读内存** —— 与游戏进程零接触；
2. **不自动化** —— 不代替玩家执行任何操作，不自动购买、不自动拖拽；
3. **不采集画面** —— 连截图都不做，不 OCR、不模板匹配。

工具实质可概括为："**替你更快地听，并替你查一张静态价格表**"。类比：把耳机音量调大、把价目表贴在显示器边上。这两件事都不违规。

**但以下三点必须如实说明，不做保票：**

1. 官方条款措辞宽泛 ——「使用第三方软件、第三方插件或应用程序以任何方式**优化或改变游戏**」，理论上任何第三方程序都落在射程内，**解释权完全在官方**；
2. ACE 具备进程扫描能力，普通常驻程序（Discord / OBS / 浏览器）在实践中不受影响，但**针对「音频识别类」工具既无公开封禁先例，也无官方背书** —— 这是空白地带，不是安全区；
3. **最大不确定性来自官方态度变化**。若官方认定此类工具破坏「听声辨宝」的博弈设计，可能单独发文禁止。届时本方案须立即停用。

> **结论：本方案落在「低风险区」，与官方明确打击的作弊形态有本质区隔，但不能承诺「不会违规」。是否使用，由使用者自行判断。**

#### C2.2 工程侧降风险措施（强制）

以下措施为设计约束，实施时不得省略：

| # | 措施 | 目的 |
|---|---|---|
| 1 | 使用标准 Win32 置顶窗口，**不做**透明穿透、**不挂钩**渲染管线 | 与 Overlay 形态彻底切割 |
| 2 | 弹窗**仅在识别到结果时短暂出现**，其余时间隐藏 | 不做常驻视觉干扰 |
| 3 | 一切输出均依赖「游戏确实播放了音效」，无音效则无输出 | 不产生任何游戏数据推断 |
| 4 | 内置一键总开关与热键隐藏 | 用户随时可停 |
| 5 | 实战模式**默认关闭**，首次开启弹出风险告知并要求确认 | 知情决策 |
| 6 | 练耳模式全程不接触游戏，作为零风险基线 | 提供可退路径 |

#### C2.3 显示方案变更：手机网页取代置顶窗口（2026-09-30 实施）

实施阶段确认了更优的显示载体：**PC 端内置 HTTP 服务，手机浏览器访问**。

| 对比项 | 游戏内置顶窗口 | 手机网页（现行方案） |
|---|---|---|
| 需要游戏切窗口化 | **是（硬前提）** | **否** |
| 覆盖游戏画面 | 视觉上是 | 否 |
| 反作弊风险 | 低但非零 | 更低，等同「手机看攻略」 |
| 硬件要求 | 无副屏时必须改显示模式 | 仅需与电脑同一 WiFi |
| 实现复杂度 | 需处理置顶 / 穿透 / 全屏冲突 | 一个 HTTP 端点 |

**结论：C2 的硬前提（游戏必须运行在无边框窗口化模式）在手机方案下不再必要。** 置顶窗口作为可选形态保留，但不作为主路径。

信号通道：

```
PC 采集 → 事件切分 → 库匹配 → HTTP :8765/api/live → 手机轮询(500ms) → 显示
```

手机页面展示：命中的音效类、候选物品列表、相似度条、其他相近音效、共用音效提示。

### C3 — 音效不足以唯一确定物品，必须引入交叉过滤（新增）

参考站 FAQ 明确指出，判决时还需结合 **占用格数、档位价、货物名称、情报** 综合判断。

问题在于：这四个维度中，前三项都要读取游戏画面才能自动获取 —— 而 C2 / §1.3 已禁止画面采集。**因此候选集收敛只能依靠玩家的手动输入。**

设计后果：工具的输出不是一个终态答案，而是**一个可交互的候选集**。玩家可以在窗口上一键点选「占 4 格」「某价格档位」，工具据此实时过滤候选。这把合规风险转移到人工操作上，同时保留了收敛能力。

具体交互设计见 §5.5。

### C4 — 录制设备必须与使用设备一致（新增）

音频模型对**录制链路**极度敏感。同一件物品，经不同声卡输出、不同录制方式采得，其频谱包络（音染）差异足以让模型误判。

因此：**采样阶段的音频设备、系统音量、耳机/扬声器选择，必须与日常使用阶段完全一致。**

若要支持多设备切换，必须为每套设备单独校准（见 §8.3）。在模型层面可通过数据增强缓解，但不能根治。

## 3. 系统架构

### 3.1 分层

| 层 | 语言 | 职责 | 运行时机 |
|---|---|---|---|
| 采集层 | C# | 系统音频回环采集、音效事件切分、特征提取 | 游戏运行时常驻 |
| 推理层 | C# | ONNX 模型推理、候选集决策、价格查表、界面展示 | 游戏运行时常驻 |
| 训练层 | Python | 样本清洗、特征工程、模型训练、导出 ONNX | 离线，按需执行 |

### 3.2 模块清单

| 模块 | 建议文件 | 职责 |
|---|---|---|
| M1 音频采集 | `AudioCapture.cs` | WASAPI Loopback 捕获系统输出音频流 |
| M2 事件检测 | `SoundEventDetector.cs` | 从连续流中切出拾取音片段，抑制背景音与无关音效 |
| M3 特征提取 | `FeatureExtractor.cs` | 生成 Mel 频谱 / MFCC |
| M4 模型推理 | `Classifier.cs` | 加载 ONNX，输出音效类 ID 与置信度 |
| M5 决策解析 | `Resolver.cs` | 音效类 → 候选物品集 → 价格排序 → 建议标记 |
| M6 数据加载 | `DataStore.cs` | 读取并热加载三个 JSON 数据文件 |
| M7 界面 | `MainWindow.cs` + `TrayIcon.cs` | 置顶小窗、候选集筛选交互、托盘图标 |
| M8 进程守护 | `GameWatcher.cs` | 检测游戏进程，按需启停采集以节省资源 |

### 3.3 工程陷阱提示

> **M3 与训练端的特征提取参数必须完全一致**，包括采样率、窗长、帧移、Mel 滤波器数量、频率上下限、是否做归一化。任何一项不一致都会导致推理结果完全失效。
>
> 处理办法：把全部特征参数抽到单一配置源 `feature_config.json`，C# 端与 Python 端共同读取同一份文件，禁止在两处各写一遍。

### 3.4 音频前处理链路（2026-09-30 实测修正，新增）

对 15 条真实素材（48kHz / 16bit / 立体声，时长 0.235~0.853s）做定量审计后，
发现三处必须修正的环节。均已落地到 `src/aq_dsp.py`，可用 `tools/ref_audit.py` 复现。

| # | 修正 | 不修正的后果 | 实测依据 |
|---|---|---|---|
| F1 | **首尾静音裁剪** | DTW 把静音帧对齐到有效音帧，跨时长配对相似度被系统性压低 | 素材静音占比 **2%~76%**；裁剪前相似度矩阵出现与声学内容无关的整块 `0.000` |
| F2 | **倒谱均值归一化 CMN** | 设备频响差异（EQ 倾斜）无处吸收，跨链路自相似骤降 | EQ 倾斜 4dB/oct 下：未归一化自相似 0.669、top-1 **11/15**；归一化后 0.948、**15/15** |
| F3 | **DTW 带宽下限含长度差** | 带宽小于两段帧数差时终点不可达，折算成伪 0 相似度 | 帧数差达 4.5 倍，`band=0.3` 时矩阵出现整行整列 `0.000` |

**F1 的实现**：以 10ms 帧 RMS 相对峰值 -45dB 为静音判据，首尾各留 20ms
保护瞬态。样本入库时即落盘裁剪后的音频，库里不存静音。

**F3 的归一化细节**：DTW 路径步数受带宽约束、恒接近 `max(ta, tb)`。
用 `(ta+tb)` 作分母时，两段时长差越大分母越小、距离被系统性抬高 ——
表现为"短音频 vs 长音频"恒得低分。故改用 `max(ta, tb)` 归一化。

**连带影响（必须处理）**：启用 CMN 后相似度的**绝对尺度**发生变化，
任何硬编码阈值都会失效。已提供 `tools/calibrate.py` 做留一交叉验证标定，
产出 `data/library/calibration.json`，`match_live.py` 启动时自动读取。

**参数尚未定稿**：F1 使平均帧数由 33 降到 18，FFT 窗长/帧移的最优值随之改变。
15 条外部素材只能证明**方向正确**，不能用来定参数 —— 参数必须在自录样本上标定。
窗长 1024→512 的对照测试显示类间相似度由 0.795 降到 0.518（可分性显著改善），
但跨链路 top-1 未同步提升，说明瓶颈在归一化而非窗长。

## 4. 数据模型

全部数据为**本地人工维护的 JSON**，不接入任何游戏接口。数据结构已与外部同类产品交叉验证，形态一致。

### 4.1 `items.json` — 物品表

```json
{
  "schemaVersion": 1,
  "updatedAt": "2026-09-30",
  "items": [
    {
      "id": "item_0001",
      "name": "军用急救包",
      "category": "消耗品",
      "tier": "purple",
      "gridSize": 4,
      "refPrice": 12800,
      "priceRange": [11500, 14200],
      "priceUpdatedAt": "2026-09-30"
    }
  ]
}
```

字段说明：

- `tier` — 品质档位，取值 `white` / `blue` / `purple` / `gold` / `red`
- `gridSize` — 占用格数，C3 交叉过滤的核心维度之一

### 4.2 `sounds.json` — 音效类表

```json
{
  "schemaVersion": 1,
  "sounds": [
    {
      "id": "sound_01",
      "label": "金属·小件·A",
      "durationMs": 576,
      "sampleCount": 42,
      "crossDeviceStable": true
    }
  ]
}
```

### 4.3 `mapping.json` — 音效到候选物品的映射

```json
{
  "schemaVersion": 1,
  "mappings": [
    {
      "soundId": "sound_01",
      "itemIds": ["item_0001", "item_0032", "item_0087"],
      "unique": false
    }
  ]
}
```

`unique: true` 表示该音效类仅对应一个物品 —— 产品价值最高的一类数据，采样阶段应优先识别并标注。

### 4.4 数据结构版本化

游戏版本更新可能替换音效资源。三个 JSON 均带 `schemaVersion` 与时间戳，模型文件带训练时的数据版本哈希。版本不匹配时工具应明确提示而非静默给出错误结果。

## 5. 关键技术选型

### 5.1 音频采集 — WASAPI Loopback

**为什么不用麦克风：** 麦克风会拾取环境噪声、键盘声与耳机漏音，信噪比远低于系统内录。WASAPI Loopback 是 Windows 原生能力，直接捕获声卡输出流。

**硬参数匹配（已实测确认）：**

| 参数 | 游戏音效实际值 | WASAPI Loopback 默认 | 结论 |
|---|---|---|---|
| 采样率 | 48000 Hz | 48000 Hz | 完全匹配，无需重采样 |
| 位深 | 16 bit | 32-bit float | 需做一次格式转换 |
| 声道 | 2（立体声） | 2 | 匹配，但需决策是否降混 |

**立体声处理决策：** 拾取音效为立体声，但左右声道信息对「识别是哪件物品」几乎无贡献，主要贡献来自声像位置（会随拖动位置变化，属于噪声）。**建议降混为单声道**再做特征提取，可减少一半计算量并提升鲁棒性。

**已知限制：** 若音频设备启用独占模式（Exclusive Mode），Loopback 可能捕获失败。界面需提供设备选择与实时电平指示。

### 5.2 音效事件检测

不采用"连续分类"，而是**先切分再识别**：

1. 以能量门限 + 谱平坦度检测瞬态起始点；
2. 从起始点前 50ms 至后 600ms 截取定长窗口（**总窗口 650ms**，依据 §5.1 实测的 576ms 音效时长）；
3. 与已知音效模板做相关性预筛，丢弃低相关片段，抑制枪声、脚步、语音、UI 点击等干扰。

> **关于"在行商购买页面弹出"的实现方式：本方案不检测游戏 UI 状态。**
> 原因是音效事件本身就是精确触发器 —— 只有当游戏真正播放了目标音效，系统才会输出结果。这样做同时达成两个目的：一是彻底避免屏幕采集行为（合规考量，见 §1.3），二是省掉 OCR 与模板匹配的工程复杂度。窗口可常驻置顶，仅在识别到结果时更新内容。

### 5.3 识别路线对比

| 维度 | 路线 A：模板匹配（MFCC + DTW） | 路线 B：Mel 谱 + CNN |
|---|---|---|
| 是否需要训练 | 否 | 是 |
| 冷启动速度 | 快，采到即用 | 慢，需先积累样本 |
| 小样本表现 | 好（每类 5~10 条即可） | 差，易过拟合 |
| 数据充足后精度 | 一般 | 高 |
| 抗噪能力 | 弱 | 强 |
| 跨设备泛化 | 弱 | 强 |
| 实现成本 | 低 | 中 |

**建议路线：** P0 阶段先上路线 A，用最低成本验证 C1；当每类样本量超过 50 条后，再切换路线 B。训练端 Python 使用 librosa + PyTorch，导出 ONNX；推理端 C# 使用 ONNX Runtime，用户机器无需 Python 运行时。

### 5.4 价格数据

不接入任何游戏接口或第三方数据服务。初版采用本地 JSON 价格表，人工维护。需要配套轻量更新流程（每赛季手动核对，或表格批量导入）。UI 必须显示价格更新日期，超过 30 天时降级为只显示物品名。

### 5.5 候选收敛矩阵（新增）

C3 约束下，工具的核心交互不是"给答案"，而是"帮你把候选砍下去"。设计如下。

**输入**：识别到的音效类 → 初始候选集（N 件物品）。

**可用的过滤维度**（全部由玩家手动点选，工具不自动读取）：

| 过滤维度 | 信息来源 | 交互方式 | 预期收敛能力 |
|---|---|---|---|
| 占用格数 | 玩家看商品区格子版式 | 点选「1×1 / 1×2 / 2×2 …」 | 强 |
| 价格档位 | 玩家看商品标价区间 | 输入或点选价格区间 | 强 |
| 品质档位 | 玩家看物品描边颜色 | 点选「白/蓝/紫/金/红」 | 中 |
| 名称首字 | 玩家看货物名称 | 输入关键字搜索 | 决定性 |
| 情报信息 | 玩家花情报探查 | 手动录入，若游戏已给出答案则直接结束 | 决定性 |

**输出**：候选集实时收敛，剩余候选按价格降序排列，并显示"当前候选 N 件，最高价值 X，最低价值 Y，建议：买/谨慎/放弃"。

**设计要点**：

- 每应用一个过滤器，窗口即时刷新，不高亮、不闪烁，避免干扰游戏操作；
- 玩家可一键清空所有过滤条件，恢复完整候选集；
- 若应用过滤后候选集为空，提示"该条件与音效不匹配，请检查"而非静默无输出。

## 6. 采样方案

**这是整个项目工作量最大、且无法被任何技术手段替代的部分。**

### 6.1 采样工具要求

| 能力 | 说明 |
|---|---|
| 一键录音 | 热键按下开始，松开结束 |
| 自动切片 | 长按连续录音时按静音段自动切分 |
| 波形预览 | 当场判断是否录糊、是否混入环境音 |
| 快速标注 | 录完立即选择物品名，写入样本库 |
| 重复度统计 | 实时显示每件物品已录样本数 |
| 临时标记 | 支持「暂不标注，稍后补」，避免打断游戏节奏 |
| 批量导出 | 输出 `samples/*.wav` + `labels.csv` |

采样工具本身应作为 P0 阶段的第一份交付物，用 C# 实现（复用 M1 的采集代码）。

### 6.2 采样标准作业流程

1. 进入训练场或安全场景，避免枪声与交火干扰；
2. 关闭背景音乐，仅保留音效通道；
3. **固定音频设备与系统音量** —— 采样与日后使用必须一致（C4）；
4. 每件物品录 **5 次以上**，覆盖不同拖拽速度（慢拖 / 快甩）；
5. **记录物品真实名称**，不要凭记忆打标；
6. 同时记录该物品的**占用格数与品质档位**，写入 `items.json`（C3 需要）；
7. 每批次结束立即导出并留存，不要攒着。

### 6.3 首轮采样目标

| 指标 | 目标值 |
|---|---|
| 覆盖音效类 | **全部约 15 种**（先覆盖音效，而非物品） |
| 每音效类样本数 | ≥ 5 |
| 样本总时长 | 约 3~5 分钟纯音效 |
| **产出结论** | **共音分组率**（见 §7.2） |

> **采样策略调整**：v0.1 阶段的目标是"覆盖 50 件物品"。参考站调研表明音效类总数约 15 种，因此首轮应**按音效类组织采样** —— 先把 15 类音效全部采齐，再逐类扩展对应的物品清单。这样能最快得出分组率。

## 7. 质量指标

### 7.1 音效类识别准确率

模型层面指标。路线 A 阶段目标 ≥ 90%，路线 B 阶段目标 ≥ 95%。评估方式：留出 20% 样本做测试集，按音效类计算混淆矩阵。

### 7.2 共音分组率 —— 核心业务指标

```
共音分组率 = 仅对应单一物品的音效类数量 / 音效类总数
```

**已确认基准：音效类总数约 15 种。**

这个数字直接决定产品价值，也是 P0 阶段的唯一目标：

| 分组率 | 结论 | 行动 |
|---|---|---|
| ≥ 0.80 | 绝大多数物品可精确识别 | 全力推进 |
| 0.50 ~ 0.80 | 部分精确、部分候选集 | 可做，需强化 §5.5 候选收敛 |
| 0.30 ~ 0.50 | 多数只能给候选集 | 依赖候选收敛能力，重新评估 |
| < 0.30 | 只能给类别提示 | 建议转「练耳工具」形态（见 §11） |

> 注意：15 个音效类面对的商品池可能包含数百件物品，因此**分组率大概率不会高**。这意味着 §5.5 的候选收敛设计不是锦上添花，而是**产品能否成立的关键**。P0 阶段除分组率外，还应统计**每类的候选数量中位数**。

### 7.3 端到端延迟

从拖拽音结束到窗口显示结果，目标 ≤ **800ms**。分解预算：

| 环节 | 预算 |
|---|---|
| 事件切分与缓冲 | 350ms（窗口 650ms，含尾部等待） |
| 特征提取 | 100ms |
| 模型推理 | 150ms |
| 决策与渲染 | 150ms |
| 余量 | 50ms |

## 10. 采样与素材的合规说明

参考站（暗区情报站）整理了 15 种拾取音效并提供下载。**不建议直接使用该素材包**，理由如下：

1. **版权归属不明** —— 音效本体版权属游戏厂商，站点为第三方「实录」整理，二次使用缺乏明确授权；
2. **技术上不可用** —— 实录文件带有录制端的设备音染，与本机链路不一致，会直接损害模型精度（C4）。

**正确做法：在本机自行录制。** 这既是版权上最干净的选择，也是技术上唯一可靠的选择。

## 11. 产品形态三路线（新增，需决策）

| | 路线一：实战辅助 | 路线二：练耳工具 | **路线三：双模式（建议）** |
|---|---|---|---|
| 定位 | 游戏中实时提示 | 离线练习听声辨物 | 前两者共用同一内核 |
| 形态 | 独立置顶小窗 | 桌面应用 / 本地网页 | 同一程序，模式切换 |
| 合规风险 | 低但非零 | **零** | 练耳零风险，实战按需开启 |
| 差异化 | 强（参考站做不到） | 弱（参考站已免费提供） | 强 |
| 依赖真实游戏 | 是 | 否 | 否（练耳）/ 是（实战） |
| 核心资产 | 音效指纹库 + 匹配引擎 | 同左 | 同左 |

**建议采纳路线三。** 核心资产是「音效 → 藏品」本地库与匹配引擎，两种使用形态共享同一套底层：

- **P0~P1 阶段**先只做本地识别内核与练耳界面 —— 零风险，可立即使用，也能验证数据质量；
- **P2 阶段**再叠加实时采集与独立窗口，进入实战模式；
- 用户全程可自主决定是否启用实战模式。
