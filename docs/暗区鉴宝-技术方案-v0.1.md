## 1. 项目定位

### 1.1 问题陈述

《暗区突围：无限》自 S7 赛季「理想国」起加入局内「战地行商」机制。玩家可在行商处购买**神秘箱子 / 神秘货物**，其内容物在交易完成前不公开。官方描述为："低价神秘货物收益整体更为稳定；高价神秘货物收益两极分化明显，既存在暴富的机会，也有不小的亏损风险。"

玩家在**拖动物品**时，游戏会播放该物品对应的持有效果音（下文统称「拖拽音」）。本工具采集该音效并反推物品身份，为购买与取舍决策提供参考。

### 1.2 产品目标

在玩家完成一次拖拽动作后 **1 秒内**，于独立窗口输出：

1. 该音效对应的究竟是**唯一物品**，还是**候选物品集合**；
2. 每个候选的**市场参考价**与**价格区间**；
3. 基于价格的**建议标记**（值得买 / 需谨慎 / 不建议）。

### 1.3 明确不做的事

| 不做 | 原因 |
|---|---|
| 不读写游戏内存 | 触发 ACE 反作弊，封号风险极高 |
| 不注入 DLL / 不 Hook 游戏进程 | 同上 |
| 不覆盖游戏画面 | Overlay 是反作弊重点监控形态，官方通报中明确提及覆盖层可能触发误报 |
| 不自动操作（自动购买 / 自动拖拽 / 自动跑刀） | 属官方「负面清单」明令禁止的脚本行为 |
| 不修改任何客户端文件 | 官方处罚规则直接列举的违规项 |
| 不采集游戏画面（截图 / OCR） | 避免任何形式的画面采集行为 |

## 2. 关键约束

约束来自实机反馈，是整套设计的出发点，不可绕过。

### C1 — 音效与物品不是一对一映射

**实机确认：部分物品有专属音效，另一些物品共用同一个音效。**

这条约束推导出四个设计后果：

1. **识别粒度是「音效事件」而非「物品」。** 系统的输出单位定义为 **音效类（Sound Class）**。
2. **核心数据结构是「音效类 → 候选物品列表」的多对多映射。**
3. **输出必须显式表达不确定性：**

   | 候选数 | 输出形态 | 产品价值 |
   |---|---|---|
   | 1 | `精确命中` — 直接给物品名与价格 | 高 |
   | 2 ~ 5 | `候选集` — 按价格排序，标注"此音效与另外 N 件物品共用" | 中 |
   | > 5 | `类别提示` — 只给物品类别与价格区间 | 低 |

4. **引入「共音分组率」作为核心业务指标**（详见 §7.2）。这个数字决定产品上限，必须在写产品代码之前测出来。

### C2 — 显示载体不覆盖游戏

已确认采用**独立窗口 / 副屏**方案，不覆盖游戏画面、不注入游戏进程。由此产生两条工程约束：

- 若游戏运行在**独占全屏（Exclusive Fullscreen）**模式，任何置顶窗口都无法显示在其上方。**要求游戏运行在无边框窗口化（Borderless Windowed）模式**，或使用第二台显示器。
- 工具自身不读取游戏画面，因此**不需要也不会实现 UI 状态识别**（详见 §5.2 末段）。

## 3. 系统架构

### 3.1 分层

| 层 | 语言 | 职责 | 运行时机 |
|---|---|---|---|
| 采集层 | C# | 系统音频回环采集、音效事件切分、特征提取 | 游戏运行时常驻 |
| 推理层 | C# | ONNX 模型推理、候选集决策、价格查表、界面展示 | 游戏运行时常驻 |
| 训练层 | Python | 样本清洗、特征工程、模型训练、导出 ONNX | 离线，按需执行 |

### 3.2 模块清单

| 模块 | 建议文件 | 职责 |
|---|---|---|
| M1 音频采集 | `AudioCapture.cs` | WASAPI Loopback 捕获系统输出音频流 |
| M2 事件检测 | `SoundEventDetector.cs` | 从连续流中切出拖拽音片段，抑制背景音与无关音效 |
| M3 特征提取 | `FeatureExtractor.cs` | 生成 Mel 频谱 / MFCC |
| M4 模型推理 | `Classifier.cs` | 加载 ONNX，输出音效类 ID 与置信度 |
| M5 决策解析 | `Resolver.cs` | 音效类 → 候选物品集 → 价格排序 → 建议标记 |
| M6 数据加载 | `DataStore.cs` | 读取并热加载三个 JSON 数据文件 |
| M7 界面 | `MainWindow.cs` + `TrayIcon.cs` | 置顶小窗与托盘图标 |
| M8 进程守护 | `GameWatcher.cs` | 检测游戏进程，按需启停采集以节省资源 |

### 3.3 工程陷阱提示

> **M3 与训练端的特征提取参数必须完全一致**，包括采样率、窗长、帧移、Mel 滤波器数量、频率上下限、是否做归一化。任何一项不一致都会导致推理结果完全失效。
>
> 处理办法：把全部特征参数抽到单一配置源 `feature_config.json`，C# 端与 Python 端共同读取同一份文件，禁止在两处各写一遍。

## 4. 数据模型

全部数据为**本地人工维护的 JSON**，不接入任何游戏接口。

### 4.1 `items.json` — 物品表

```json
{
  "schemaVersion": 1,
  "updatedAt": "2026-09-30",
  "items": [
    {
      "id": "item_0001",
      "name": "军用急救包",
      "category": "消耗品",
      "tier": "purple",
      "refPrice": 12800,
      "priceRange": [11500, 14200],
      "priceUpdatedAt": "2026-09-30"
    }
  ]
}
```

### 4.2 `sounds.json` — 音效类表

```json
{
  "schemaVersion": 1,
  "sounds": [
    {
      "id": "sound_007",
      "label": "金属·小件·A",
      "sampleCount": 42,
      "durationMs": 380,
      "crossDeviceStable": true
    }
  ]
}
```

### 4.3 `mapping.json` — 音效到候选物品的映射

```json
{
  "schemaVersion": 1,
  "mappings": [
    {
      "soundId": "sound_007",
      "itemIds": ["item_0001", "item_0032", "item_0087"],
      "unique": false
    }
  ]
}
```

`unique: true` 表示该音效类仅对应一个物品 —— 这是产品价值最高的一类数据，采样阶段应优先识别并标注。

### 4.4 数据结构版本化

游戏版本更新可能替换音效资源。三个 JSON 均带 `schemaVersion` 与时间戳，模型文件带训练时的数据版本哈希。版本不匹配时工具应明确提示而非静默给出错误结果。

## 5. 关键技术选型

### 5.1 音频采集 — WASAPI Loopback

**为什么不用麦克风：** 麦克风会拾取环境噪声、键盘声与耳机漏音，信噪比远低于系统内录。WASAPI Loopback 是 Windows 原生能力，直接捕获声卡输出流，是最干净的游戏音频源。C# 侧使用 NAudio 封装调用。

**已知限制：** 若音频设备启用独占模式（Exclusive Mode），Loopback 可能捕获失败。界面需提供设备选择与实时电平指示，让用户能一眼确认采集是否正常。

### 5.2 音效事件检测

不采用"连续分类"，而是**先切分再识别**：

1. 以能量门限 + 谱平坦度检测瞬态起始点；
2. 从起始点前 50ms 至后 500ms 截取定长窗口；
3. 与已知音效模板做相关性预筛，丢弃低相关片段，抑制枪声、脚步、语音、UI 点击等干扰。

> **关于"在行商购买页面弹出"的实现方式：本方案不检测游戏 UI 状态。**
> 原因是音效事件本身就是精确触发器 —— 只有当游戏真正播放了目标音效，系统才会输出结果。这样做同时达成两个目的：一是彻底避免屏幕采集行为（合规考量，见 §1.3），二是省掉 OCR 与模板匹配的工程复杂度。窗口可常驻置顶，仅在识别到结果时更新内容。

### 5.3 识别路线对比

| 维度 | 路线 A：模板匹配（MFCC + DTW） | 路线 B：Mel 谱 + CNN |
|---|---|---|
| 是否需要训练 | 否 | 是 |
| 冷启动速度 | 快，采到即用 | 慢，需先积累样本 |
| 小样本表现 | 好（每类 5~10 条即可） | 差，易过拟合 |
| 数据充足后精度 | 一般 | 高 |
| 抗噪能力 | 弱 | 强 |
| 跨设备泛化 | 弱（不同声卡存在音染差异） | 强 |
| 实现成本 | 低 | 中 |
| 可解释性 | 高（可回放比对） | 低 |

**建议路线：** P0 阶段先上路线 A，用最低成本验证卡点 C1；当每类样本量超过 50 条后，再切换路线 B。训练端 Python 使用 librosa + PyTorch，导出 ONNX；推理端 C# 使用 ONNX Runtime，无需 Python 运行时环境。

### 5.4 价格数据

不接入任何游戏接口或第三方数据服务。初版采用本地 JSON 价格表，人工维护。需要配套一个轻量更新流程 —— 每赛季手动核对一次，或提供表格批量导入功能。UI 必须显示价格更新日期，超过 30 天时降级为只显示物品名，不显示价格建议。

## 6. 采样方案

**这是整个项目工作量最大、且无法被任何技术手段替代的部分。** 没有样本，模型无从谈起。

### 6.1 采样工具要求

| 能力 | 说明 |
|---|---|
| 一键录音 | 热键按下开始，松开结束 |
| 自动切片 | 长按连续录音时按静音段自动切分 |
| 波形预览 | 当场判断是否录糊、是否混入环境音 |
| 快速标注 | 录完立即选择物品名，写入样本库 |
| 重复度统计 | 实时显示每件物品已录样本数 |
| 批量导出 | 输出 `samples/*.wav` + `labels.csv` |

采样工具本身应作为 P0 阶段的第一份交付物，用 C# 实现（复用 M1 的采集代码）。

### 6.2 采样标准作业流程

1. 进入训练场或安全场景，避免枪声与交火干扰；
2. 关闭背景音乐，仅保留音效通道；
3. **固定音频设备与系统音量** —— 采样与日后使用必须一致，否则音染差异会毁掉模型；
4. 每件物品录 **5 次以上**，覆盖不同拖拽速度（慢拖 / 快甩）；
5. **记录物品真实名称**，不要凭记忆打标；
6. 每批次结束立即导出并留存，不要攒着。

### 6.3 首轮采样目标

| 指标 | 目标值 |
|---|---|
| 覆盖物品数 | ≥ 50 |
| 每物品样本数 | ≥ 5 |
| 样本总时长 | 约 3~5 分钟纯音效 |
| **产出结论** | **共音分组率**（见 §7.2） |

首轮采样不追求覆盖全部物品，追求的是**尽快得出分组率数字**，判定项目是否值得继续。

## 7. 质量指标

### 7.1 音效类识别准确率

模型层面指标。路线 A 阶段目标 ≥ 90%，路线 B 阶段目标 ≥ 95%。评估方式：留出 20% 样本做测试集，按音效类计算混淆矩阵。

### 7.2 共音分组率 —— 核心业务指标

```
共音分组率 = 仅对应单一物品的音效类数量 / 音效类总数
```

这个数字直接决定产品价值，也是 P0 阶段的唯一目标：

| 分组率 | 结论 | 行动 |
|---|---|---|
| ≥ 0.80 | 绝大多数物品可精确识别 | 全力推进 |
| 0.50 ~ 0.80 | 部分精确、部分候选集 | 可做，需强化候选集展示 |
| 0.30 ~ 0.50 | 多数只能给候选集 | 谨慎，重新评估产品定位 |
| < 0.30 | 只能给类别提示 | 建议放弃或改做"类别级提示"轻量版 |

### 7.3 端到端延迟

从拖拽音结束到窗口显示结果，目标 ≤ **800ms**。分解预算：

| 环节 | 预算 |
|---|---|
| 事件切分与缓冲 | 300ms |
| 特征提取 | 100ms |
| 模型推理 | 150ms |
| 决策与渲染 | 150ms |
| 余量 | 100ms |

## 8. 分阶段计划

| 阶段 | 目标 | 交付物 | 通过标准 |
|---|---|---|---|
| **P0 可行性验证** | 验证音效可分性 | 采样工具 + 首轮样本集 + 分组率报告 | 分组率 ≥ 0.50 |
| **P1 识别内核** | 打通采集→识别→输出 | 无界面的命令行程序 | 识别准确率 ≥ 90% |
| **P2 界面与集成** | 独立窗口 + 托盘 + 价格表 | 可日常使用的工具 | 端到端延迟 ≤ 800ms |
| **P3 打磨** | 误报抑制、设备校准、自启动 | 发布版 | 连续使用 2 小时无漏识别、无误报 |

> **纪律要求：P0 通过标准达成之前，不写任何 P1 及以后的产品代码。**

## 9. 风险登记表

| # | 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|---|
| R1 | 共音分组率过低，产品价值不足 | 中 | 高 | P0 优先测出该数字；若过低则转向类别级提示或终止项目 |
| R2 | 账号因第三方工具被处罚 | 低 | 极高 | 严格限定为外部音频采集 + 独立窗口；拒不接受任何形式的游戏内覆盖 |
| R3 | ACE 将音频回环判定为异常行为 | 极低 | 高 | 本方案不接触游戏进程、不注入、不采集画面；一旦出现异常封禁记录立即停用 |
| R4 | 不同音频设备音染导致模型泛化失败 | 中 | 中 | 采样与使用设备保持一致；P3 阶段引入设备校准步骤 |
| R5 | 游戏版本更新替换音效资源 | 中 | 中 | 三份 JSON 与模型文件均版本化；更新后重采受影响物品 |
| R6 | 价格数据过期导致错误建议 | 高 | 中 | UI 标注价格更新日期；超过 30 天降级只显示物品名 |
| R7 | 事件切分误触发（枪声、脚步被当成拖拽音） | 高 | 中 | 提高相关性阈值 + 置信度门限；低于门限不输出结果，宁可不报不可错报 |

### R2 补充说明（请务必阅读）

官方《处罚规则》原文列举："使用第三方软件、第三方插件或应用程序以任何方式**优化或改变游戏**……视情节严重程度而定，包括但不限于取消排名、封禁账号甚至追加封禁设备的惩罚。"

官方《负面清单 10 条》第 2 条亦规定：使用"游戏明令禁止或不建议的软硬件工具"将面临处罚。

ACE 反作弊具备**硬件指纹（HWID）识别、服务器端行为分析、社交图谱检测**三重能力，公开通报中封禁上限为**十年账号封禁 + 设备封禁**。

本方案通过「不接触游戏进程、不覆盖画面、不自动化操作、不采集画面」四项约束，将触发条件压到最低。但需要明确：

> **残余风险不为零。是否使用、是否承担，由使用者自行判断。**

## 附录 A — 术语表

| 术语 | 含义 |
|---|---|
| 音效类（Sound Class） | 一组听感相同、可被模型视为同一类的拖拽音 |
| 候选集 | 某个音效类可能对应的全部物品的集合 |
| 共音分组率 | 仅对应单一物品的音效类占全部音效类的比例 |
| 拖拽音 | 玩家在界面中拖动或持有一件物品时播放的效果音 |
